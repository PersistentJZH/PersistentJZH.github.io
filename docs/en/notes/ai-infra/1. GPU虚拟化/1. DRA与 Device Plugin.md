# DRA and Device Plugins

Kubernetes has historically relied mainly on **Device Plugins** to manage specialized hardware such as GPUs, FPGAs, RDMA NICs, SmartNICs, MIG instances, and vGPUs. A Device Plugin represents hardware as extended resources, such as `nvidia.com/gpu: 1`, allowing the scheduler to allocate quantities much as it handles CPU and memory.

**DRA**, Dynamic Resource Allocation, upgrades a device request from a resource name and integer to native Kubernetes API objects: `DeviceClass`, `ResourceSlice`, `ResourceClaim`, and `ResourceClaimTemplate`. Its goal is not arbitrary GPU hot-plugging into running Pods, but more structured description, selection, allocation, and preparation of devices before Pod scheduling and startup.

In brief:

- Device Plugin: simple, mature, and widely supported; suitable for integer device requests, such as one GPU.
- DRA: more expressive; supports selection by model, memory, topology, partitioning, and sharing capability, while exposing allocation through Kubernetes APIs.

## Background

Kubernetes' original native resource model mainly targeted general-purpose CPU, memory, and storage. GPUs and high-speed NICs have several special requirements:

- Initialization requires vendor drivers, runtimes, device files, environment variables, mounts, CDI configuration, and related logic.
- Resources generally cannot be naturally overcommitted like CPU; many cases require integer allocation.
- A node may contain different device models, or one device may be split into multiple MIG / vGPU / VF instances.
- Devices have attributes such as health, NUMA and PCIe topology, memory capacity, bandwidth, and driver version.
- AI training and inference need requests such as "A100 80G," "GPU and RDMA NIC on the same NUMA node," "prefer H100, otherwise A100," or "allow multiple containers to share one resource."

Device Plugins solved the first-stage problem: making Kubernetes discover and allocate this hardware. DRA addresses the next stage: understanding device capabilities and allocation state through native, structured, schedulable objects.

## History

### Device Plugin History

Device Plugins arose because Kubernetes cannot embed vendor logic for every hardware type. GPUs, FPGAs, RDMA, QAT, DPUs, and NPUs have different drivers and initialization procedures. Modifying kubelet or the scheduler for each would make Kubernetes core difficult to maintain.

Their evolution is roughly:

| Release | Stage | Description |
| --- | --- | --- |
| Kubernetes v1.8 | Alpha | Introduced the Device Plugin framework for vendor-neutral discovery, reporting, and allocation of external devices. |
| Kubernetes v1.10 | Beta | Device Plugins entered Beta and gradually became the mainstream integration for GPUs and other specialized hardware. |
| Kubernetes v1.26 | Stable | kubelet's internal Device Manager reached GA, but the Device Plugin API itself remained non-stable, so API-version compatibility still matters. |

Vendors can run a plugin process on each node without changing Kubernetes core. Through kubelet's gRPC registration interface, the plugin reports its resource name, device list, and health. kubelet then reports these resources to the API Server through Node `status.capacity` / `status.allocatable`.

Typical names are extended-resource names:

```text
nvidia.com/gpu
amd.com/gpu
intel.com/qat
rdma/shared_hca
example.com/foo
```

The success of Device Plugins comes from their simplicity:

- Applications only need to set `resources.limits` in the Pod.
- The scheduler only needs to check whether a node has enough of the extended resource.
- At container creation, kubelet calls the plugin's `Allocate` method, which returns runtime configuration such as device files, environment variables, mounts, and CDI device names.

Their limitations also follow from this simple model:

- The scheduler primarily sees `resourceName -> integer count`, with limited understanding of device attributes.
- Resources are exposed only as integers, without directly expressing fine-grained memory, bandwidth, or partition-capacity requirements.
- Kubernetes core does not support sharing one Device Plugin device among multiple Pods / containers. Vendors can work around this through virtual resources, MIG, or time slicing, but those semantics are outside the core API.
- Device selection usually relies on node labels, annotations, private plugin configuration, or scheduling extensions rather than a unified Pod API.
- Historically, standard Kubernetes objects have struggled to clearly represent a particular device's allocation, health, sharing relationships, and partition relationships.

### DRA History

DRA aims to make device allocation a native Kubernetes API rather than only a node-local kubelet plugin protocol.

Its approximate evolution is:

| Release | Stage | Description |
| --- | --- | --- |
| Kubernetes v1.26 | Alpha | Introduced the DRA alpha API. The earliest version generalized the PVC/PV model for requesting and sharing arbitrary resources. |
| Kubernetes v1.30 | Redesign | Introduced structured parameters, shifting requests from vendor-private parameters toward device attributes the scheduler could understand. |
| Kubernetes v1.32 | Beta | The new DRA model entered Beta but was disabled by default; classic DRA from v1.26–v1.31 was no longer the direction of development. |
| Kubernetes v1.34+ | Stable / enabled by default | Core DRA reached GA and became enabled by default, using the stable `resource.k8s.io/v1` API. Current official task documentation generally requires v1.34 or later. |
| Kubernetes v1.36 | Expanded capabilities | Prioritized candidate requests became stable; extended-resource compatibility, partitionable devices, device taints, binding conditions, and resource health continued to mature. |

DRA's key change is that a resource is no longer just an integer on a Node. Drivers publish `ResourceSlice` objects describing device pools; administrators or drivers define `DeviceClass` objects; applications declare requirements with `ResourceClaim`.

The scheduler can therefore participate directly in device selection during scheduling, rather than choosing a node first and leaving kubelet to select a device locally.

## How Device Plugins Work

### Component Relationships

The central Device Plugin components run locally on the node:

```text
Device Plugin DaemonSet
        |
        | gRPC over Unix socket
        v
kubelet Device Manager
        |
        | Node status: capacity / allocatable
        v
API Server
        |
        | scheduler sees extended resources
        v
kube-scheduler
```

Plugins usually run as DaemonSets on nodes with devices, but can also run through operating-system packages or manually. Because they access kubelet's device-plugin directory and host devices, they generally require privileged permissions.

Key paths:

```text
/var/lib/kubelet/device-plugins/
/var/lib/kubelet/device-plugins/kubelet.sock
```

`kubelet.sock` is kubelet's registration socket. After starting its own gRPC server, the plugin registers with kubelet through this socket.

### Registration

After startup, a Device Plugin roughly follows these steps:

1. Initialize vendor devices: discover GPUs, check drivers, and read health status.
2. Create its Unix socket under `/var/lib/kubelet/device-plugins/`.
3. Implement the Device Plugin gRPC API, whose main methods include:
   - `ListAndWatch`: continuously report the device list and health status.
   - `Allocate`: return device files, environment variables, mounts, annotations, CDI device names, and related configuration when containers are created.
   - `GetPreferredAllocation`: optionally suggest a more suitable device combination to kubelet.
   - `PreStartContainer`: optionally perform device resets or similar actions before container startup.
4. Register a resource name, such as `nvidia.com/gpu`, through kubelet's `Registration` service.
5. kubelet writes the healthy-device count into Node status.

After registration, Node status includes resources like:

```yaml
status:
  capacity:
    nvidia.com/gpu: "8"
  allocatable:
    nvidia.com/gpu: "8"
```

If a device fails, the plugin reports it as unhealthy through `ListAndWatch`. kubelet reduces `allocatable` to prevent new Pods from being assigned the failed device. Pods already bound to it usually are not migrated automatically; instead, the failure appears as an application or container-runtime error.

### How Applications Use Device Plugins

Applications only need to declare extended resources in their container resource configuration. For a GPU:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-demo
spec:
  restartPolicy: Never
  containers:
  - name: cuda
    image: nvidia/cuda:12.4.1-base-ubuntu22.04
    command: ["nvidia-smi"]
    resources:
      limits:
        nvidia.com/gpu: 1
```

Points to remember:

- Device resources such as GPUs are usually specified only under `limits`.
- Extended resources must be integers; `0.5` is not allowed.
- They cannot be overcommitted like CPU.
- The scheduler filters by resource name and count. kubelet's Device Manager and the plugin select the particular card locally.

Traditional GPU-model scheduling usually relies on node labels, such as those generated by NVIDIA GPU Feature Discovery / Node Feature Discovery:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: a100-demo
spec:
  nodeSelector:
    nvidia.com/gpu.product: NVIDIA-A100-SXM4-80GB
  containers:
  - name: app
    image: nvidia/cuda:12.4.1-base-ubuntu22.04
    command: ["sleep", "3600"]
    resources:
      limits:
        nvidia.com/gpu: 1
```

This works, but is fundamentally node-level filtering plus a device-count request. On nodes with mixed devices, MIG profiles, or NUMA/PCIe topologies, node labels alone cannot precisely express which device a container will actually receive.

### Common Operational Checks

Check whether a node reports device resources:

```bash
kubectl describe node <node-name> | grep -A5 -E "Capacity|Allocatable|nvidia.com/gpu"
```

Inspect the node's complete allocatable resources:

```bash
kubectl get node <node-name> -o jsonpath='{.status.allocatable}' | jq
```

Inspect the plugin DaemonSet:

```bash
kubectl get ds -A | grep -i device
kubectl logs -n <namespace> ds/<device-plugin-daemonset>
```

Check whether a Pod cannot be scheduled because of insufficient resources:

```bash
kubectl describe pod <pod-name>
kubectl get events --sort-by=.lastTimestamp
```

## How DRA Works

### Core Objects

DRA uses the `resource.k8s.io/v1` API. Its main objects are:

| Object | Creator | Purpose |
| --- | --- | --- |
| `ResourceSlice` | DRA driver | Describes a device pool's devices, node accessibility, attributes, and capacity. |
| `DeviceClass` | Cluster administrator or driver | Defines a requestable device class and how devices are selected. |
| `ResourceClaim` | Workload operator or controller | Declares the devices a workload needs; multiple Pods / containers can reference it to share a resource. |
| `ResourceClaimTemplate` | Workload operator | A template, usually used by Deployments / Jobs / StatefulSets, that creates a separate `ResourceClaim` for every Pod. |

The storage concepts PVC and StorageClass are useful analogies, but not exact equivalents:

- `DeviceClass`, like `StorageClass`, defines a category of requestable resources.
- `ResourceClaim`, like `PersistentVolumeClaim`, expresses workload resource requirements.
- `ResourceSlice` is the device inventory and attributes published by the driver to the scheduler.

### DRA Scheduling Flow

A typical flow is:

```text
DRA driver publishes ResourceSlices
        |
        v
Admin creates DeviceClasses
        |
        v
User creates ResourceClaim / ResourceClaimTemplate
        |
        v
Pod references claims in spec.resourceClaims
        |
        v
kube-scheduler allocates matching devices and chooses a node
        |
        v
kubelet calls DRA driver NodePrepareResources
        |
        v
container starts with prepared devices
        |
        v
Pod deletion -> NodeUnprepareResources -> cleanup
```

The largest difference from Device Plugins is that DRA selects resources within the Kubernetes scheduling model. The scheduler sees attributes and capacity in `ResourceSlice` and can consider device allocation together with node selection.

### Enabling and Checking DRA in a Cluster

Core DRA is now stable and enabled by default in current Kubernetes, but versions still matter:

- Kubernetes v1.34 or later is recommended.
- `resource.k8s.io/v1` is the stable API.
- Some advanced features remain beta or alpha; check their feature gates and API groups.
- Older drivers may still depend on `resource.k8s.io/v1beta1` or `resource.k8s.io/v1beta2`.

Check whether the cluster supports DRA:

```bash
kubectl get deviceclasses
kubectl api-resources --api-group=resource.k8s.io
```

A common error when it does not is:

```text
error: the server doesn't have a resource type "deviceclasses"
```

After installing a DRA driver, check whether it published devices:

```bash
kubectl get resourceslices
kubectl get resourceslice <name> -o yaml
```

### DeviceClass Example

`DeviceClass` defines a category of requestable devices. This example defines a GPU class managed by the `gpu.example.com` driver:

```yaml
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: gpu.example.com
spec:
  selectors:
  - cel:
      expression: |-
        device.driver == "gpu.example.com" &&
        device.attributes["gpu.example.com"].type == "gpu"
```

The `selectors` use CEL expressions. Available fields depend on the attributes and capacity the driver publishes in `ResourceSlice`.

An administrator can first inspect the `ResourceSlice`:

```bash
kubectl get resourceslice <resourceslice-name> -o yaml
```

A simplified `ResourceSlice` might look like this:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceSlice
metadata:
  name: node-a-gpu-slice
spec:
  driver: gpu.example.com
  nodeName: node-a
  pool:
    name: node-a
    generation: 1
    resourceSliceCount: 1
  devices:
  - name: gpu-0
    attributes:
      gpu.example.com/type:
        string: gpu
      gpu.example.com/model:
        string: A100
    capacity:
      gpu.example.com/memory:
        value: 80Gi
```

Attribute naming varies by driver. Follow its documentation and the actual `ResourceSlice` contents.

### ResourceClaimTemplate Example

Use `ResourceClaimTemplate` when each Pod should receive an independent device allocation with the same configuration.

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: a100-claim-template
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.example.com
          allocationMode: ExactCount
          count: 1
          selectors:
          - cel:
              expression: |-
                device.attributes["gpu.example.com"].model == "A100" &&
                device.capacity["gpu.example.com"].memory == quantity("80Gi")
```

This means:

- Select devices from the `gpu.example.com` `DeviceClass`.
- Request exactly one device.
- Its model attribute must be A100.
- Its capacity must satisfy 80Gi of GPU memory.

### Referencing ResourceClaimTemplate from a Pod

A Pod references claims in two places:

- `spec.resourceClaims`: exposes a claim or claim template to the Pod.
- `containers[].resources.claims`: specifies which claim a container actually uses.

Example:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: dra-gpu-job
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: trainer
        image: ubuntu:24.04
        command: ["sleep", "3600"]
        resources:
          claims:
          - name: gpu
      resourceClaims:
      - name: gpu
        resourceClaimTemplateName: a100-claim-template
```

When the Job creates Pods, Kubernetes generates an independent `ResourceClaim` for each from `a100-claim-template`. The scheduler selects a matching device for the claim and schedules the Pod onto a node that can access it.

### ResourceClaim Example

To share the same device resource among containers or Pods, create a `ResourceClaim` manually and reference it from the Pods.

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: shared-gpu-claim
spec:
  devices:
    requests:
    - name: gpu
      exactly:
        deviceClassName: gpu.example.com
        allocationMode: ExactCount
        count: 1
        selectors:
        - cel:
            expression: device.attributes["gpu.example.com"].model == "A100"
```

A Pod referencing that claim:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: two-container-shared-gpu
spec:
  containers:
  - name: worker-a
    image: ubuntu:24.04
    command: ["sleep", "3600"]
    resources:
      claims:
      - name: shared-gpu
  - name: worker-b
    image: ubuntu:24.04
    command: ["sleep", "3600"]
    resources:
      claims:
      - name: shared-gpu
  resourceClaims:
  - name: shared-gpu
    resourceClaimName: shared-gpu-claim
```

This expresses two containers referring to the same `ResourceClaim`. Whether sharing is safe still depends on the device, driver, isolation mechanism, and workload.

### Can DRA Request Less Than a Whole GPU?

**The DRA API supports modeling and scheduling portions of a GPU. Whether you can actually request half a card, 8Gi of GPU memory, or a GPU slice depends on corresponding support in the DRA driver and underlying hardware / runtime.**

First, discard a common misconception: traditional extended resources do not support fractional requests. Kubernetes does not support requesting a GPU this way:

```yaml
resources:
  limits:
    nvidia.com/gpu: 0.5
```

Extended resources retain integer semantics. DRA addresses a different problem: expanding "one device" from a whole physical card into a driver-defined logical device or consumable capacity.

#### Approach One: Request a Logical Device

In DRA, `count: 1` requests one matching device, which need not equal one whole physical GPU. It may be a logical device exposed by the DRA driver, such as:

- A MIG instance.
- A vGPU slice.
- A GPU profile partitioned in advance by the driver.
- An abstract group of devices.

For example, if the driver publishes different MIG profiles in `ResourceSlice`, a selector can request a particular profile:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: mig-1g-claim-template
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.example.com
          allocationMode: ExactCount
          count: 1
          selectors:
          - cel:
              expression: device.attributes["gpu.example.com"].profile == "1g.5gb"
```

This YAML still uses `count: 1`, but requests one `1g.5gb` logical device rather than an entire physical GPU.

#### Approach Two: Partitionable Devices

`partitionable devices` describes multiple logical devices sharing the same underlying physical resources. A typical example is a GPU split into logical instances that consume memory, compute, or other counters on one physical card.

The DRA driver can publish shared counters and logical devices in `ResourceSlice`, allowing the scheduler to recognize that they cannot all be allocated without limit. If the physical device has only 8Gi and two logical devices each consume 6Gi, at most one can be allocated.

Simplified example:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceSlice
metadata:
  name: gpu-counterset
spec:
  driver: gpu.example.com
  nodeName: node-a
  pool:
    name: node-a
    generation: 1
    resourceSliceCount: 2
  sharedCounters:
  - name: gpu-0-counters
    counters:
      memory:
        value: 8Gi
---
apiVersion: resource.k8s.io/v1
kind: ResourceSlice
metadata:
  name: gpu-logical-devices
spec:
  driver: gpu.example.com
  nodeName: node-a
  pool:
    name: node-a
    generation: 1
    resourceSliceCount: 2
  devices:
  - name: gpu-0-slice-a
    consumesCounters:
    - counterSet: gpu-0-counters
      counters:
        memory:
          value: 6Gi
  - name: gpu-0-slice-b
    consumesCounters:
    - counterSet: gpu-0-counters
      counters:
        memory:
          value: 6Gi
```

This lets Kubernetes understand conflicts over underlying resources between logical devices instead of seeing unrelated extended-resource integers.

#### Approach Three: Consumable Capacity

`consumable capacity` represents deducting requested capacity from one device. A DRA driver can declare that a device permits multiple allocations:

```yaml
allowMultipleAllocations: true
```

It then declares consumable capacity on the device, such as memory or bandwidth:

```yaml
capacity:
  memory:
    value: 40Gi
```

Users request part of that capacity in a `ResourceClaim` or `ResourceClaimTemplate`:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: gpu-memory-claim-template
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.example.com
          capacity:
            requests:
              memory: 8Gi
```

The scheduler deducts `8Gi` from the device's total capacity and ensures that all claims together do not exceed it. Allocation results also record the consumed capacity and share ID.

There is a critical boundary: **DRA handles declarations, scheduling, accounting, and passing allocation results to the driver; it does not itself isolate GPU memory or CUDA compute.**

In other words:

- The scheduler can know that a Pod requested 8Gi of GPU memory.
- The driver must actually enforce that 8Gi limit.
- Underlying hardware, the runtime, or user-space components must provide isolation.
- If the driver only allocates whole cards, detailed DRA YAML can still produce only a whole physical or logical device.

A more precise way to evaluate support is:

| Question | Answer |
| --- | --- |
| Is `nvidia.com/gpu: 0.5` supported? | No. Traditional extended resources are integers. |
| Does DRA `count: 1` always mean one physical card? | No. It depends on whether the driver exposes whole cards or logical devices. |
| Can DRA request a MIG / vGPU slice? | It can model them if the DRA driver exposes these logical devices. |
| Can DRA request capacity such as 8Gi of memory? | Consumable capacity can model this if the driver and feature gates support it. |
| Does DRA isolate GPU memory itself? | No. Isolation comes from the driver, hardware, runtime, or components such as HAMi. |

### DRA Extended-Resource Compatibility

DRA also provides a migration path compatible with the old extended-resource model. Administrators can declare `extendedResourceName` on a `DeviceClass`:

```yaml
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: gpu.example.com
spec:
  selectors:
  - cel:
      expression: device.driver == "gpu.example.com"
  extendedResourceName: example.com/gpu
```

Applications can then keep using the old syntax:

```yaml
resources:
  limits:
    example.com/gpu: 1
```

The scheduler maps the extended-resource request to DRA allocation. This is useful for migration:

- The platform gradually switches from Device Plugins to DRA drivers.
- Application YAML remains unchanged initially.
- Nodes or resource types can migrate gradually within one cluster.

DRA also supports a special prefix form:

```yaml
resources:
  limits:
    deviceclass.resource.kubernetes.io/gpu.example.com: 1
```

This requests a specified number of devices directly from a `DeviceClass`; Kubernetes generates the corresponding DRA claim.

## Usage Differences

### The Most Visible YAML Difference

Device Plugin：

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

DRA：

```yaml
resources:
  claims:
  - name: gpu
resourceClaims:
- name: gpu
  resourceClaimTemplateName: a100-claim-template
```

Device Plugins put requests in the container's `resources.limits`. DRA puts them in separate claim objects, which Pods / containers reference.

### Detailed Comparison

| Dimension | Device Plugin | DRA |
| --- | --- | --- |
| Kubernetes API form | Extended resources such as `vendor.com/resource: count`. | Native `DeviceClass`, `ResourceSlice`, `ResourceClaim`, and `ResourceClaimTemplate` objects. |
| User declaration | Integer quantity in container `resources.limits`. | Declare a claim, then reference it in the Pod / container. |
| Scheduler visibility | Mainly the available integer count of an extended resource on a node. | Device classes, attributes, capacity, claim requirements, and slices published by drivers. |
| Device filtering | Usually node labels, nodeSelector, affinity, or private plugin mechanisms. | Structured CEL filtering of device attributes and capacity. |
| Resource units | Integers, without fractions or native capacity semantics. | More complex device, capacity, sharing, and partitioning semantics, depending on driver and feature gates. |
| Sharing | Core semantics do not support sharing one device between containers; vendors use virtual resources or private mechanisms. | Containers / Pods can share one `ResourceClaim`; v1.36 capabilities such as consumable capacity further improve fine-grained sharing. |
| Lifecycle | kubelet calls `Allocate` during container creation. | Scheduler allocates claims; kubelet calls DRA driver prepare / unprepare. |
| Allocation results | Mainly inspected locally in kubelet and through the PodResources API. | `ResourceClaim.status` records allocation; `ResourceSlice` and claims are Kubernetes objects visible at cluster level. |
| Operational complexity | Lower, with mature NVIDIA / AMD / Intel / RDMA plugins and ecosystem. | Higher, requiring newer Kubernetes and a DRA-compatible driver. |
| Migration cost | Simple application syntax and a large installed base. | More complex native syntax; DRA extended resources can preserve legacy syntax. |
| Suitable workloads | Whole GPUs, static MIG, basic GPU scheduling, and existing production clusters. | Complex device selection, dynamic partitioning, fine-grained sharing, topology awareness, coordinated devices, and future GPU virtualization platforms. |

### Scheduling Semantics

With Device Plugins, the scheduler reasons approximately as follows:

```text
Pod wants nvidia.com/gpu = 1
Node A allocatable nvidia.com/gpu = 4
Node A passes
```

The scheduler has no unified structured view of the particular GPU on Node A, its memory, PCIe topology, NUMA relationship, or partitioning. Node labels allow coarse filtering, but do not provide native understanding of individual-device attributes.

With DRA, scheduling looks more like:

```text
Pod references ResourceClaim
ResourceClaim wants DeviceClass gpu.example.com
selectors require model=A100 and memory=80Gi
ResourceSlices say node-a has gpu-0 satisfying the claim
scheduler reserves that allocation and binds Pod to node-a
```

DRA moves the choice of device into scheduling, making device allocation and Pod placement part of the same decision.

### Sharing Semantics

Device Plugins default to exclusive integer devices. If a Pod requests `nvidia.com/gpu: 1`, Kubernetes treats it as consuming one integer resource that cannot be allocated again.

Vendors can provide sharing or virtualization through:

- Splitting a physical GPU into MIG instances and exposing different extended resources.
- Time slicing, exposing one physical GPU as multiple logical replicas.
- vGPU / MPS / private schedulers / webhooks / annotations.

These approaches work, but Kubernetes core sees only extended-resource integers, without their underlying sharing relationships or capacity constraints.

DRA places sharing semantics in the API:

- Multiple containers can reference one `ResourceClaim`.
- Multiple Pods can reference one manually created `ResourceClaim`.
- Consumable capacity allows multiple claims to consume different amounts from one device.
- Partitionable devices express shared underlying-resource constraints when one physical device is divided into logical devices.

Availability depends on the Kubernetes version, feature gates, and specific DRA driver.

### Observability

Common Device Plugin observation points include:

- Node `status.capacity` / `status.allocatable`。
- Device Plugin DaemonSet logs.
- kubelet PodResources API。
- Device monitoring components such as DCGM exporter.
- Starting in v1.36, `allocatedResourcesStatus` can report device health in Pod status.

DRA additionally provides:

- `kubectl get deviceclasses`
- `kubectl get resourceslices`
- `kubectl get resourceclaims`
- `ResourceClaim.status.allocation`
- DRA driver prepare / unprepare metrics and logs.
- New capabilities such as DRA resource health, device taints, and resource-pool status.

## Choosing Between Them

### When to Keep Using Device Plugins

Device Plugins remain practical when:

- You only request whole GPUs, such as `nvidia.com/gpu: 1`.
- NVIDIA GPU Operator / NVIDIA device plugin already runs reliably in the cluster.
- Applications do not need complex selection by individual-card attributes.
- GPU node models are fairly uniform and node labels express scheduling requirements adequately.
- Production stability takes priority, and you are not ready to introduce DRA drivers and APIs.

For example, Device Plugins are sufficient for most basic GPU inference services, ordinary training Jobs, and single-tenant GPU clusters.

### When to Evaluate DRA First

DRA deserves closer evaluation when you need:

- Selection by device attributes such as model, memory, driver capabilities, MIG profile, or NIC bandwidth.
- Precise allocation of particular devices on nodes containing mixed hardware.
- Multiple containers or Pods sharing the same device resource.
- Dynamic partitioning, consumable capacity, or device taints / tolerations.
- Allocation results exposed as Kubernetes objects for controllers, auditing, or the platform layer.
- A unified scheduling model for GPUs, RDMA, DPUs, storage accelerators, and other resources.
- Migration from private annotations / webhooks / scheduler extenders to standard Kubernetes APIs.

For AI infrastructure, DRA is better suited to future GPU virtualization and heterogeneous-resource orchestration platforms because it gives schedulers, autoscalers, and operators clearer extension points.

## Migration Recommendations

Do not interpret migration to DRA as replacing every Device Plugin at once. A steadier path is:

1. Keep the existing Device Plugin production path stable.
2. Run Kubernetes v1.34+ in a test cluster and install the vendor's DRA driver.
3. Verify the basic lifecycles of `DeviceClass`, `ResourceSlice`, and `ResourceClaim` first.
4. Test `ResourceClaimTemplate` with a noncritical Job.
5. If application YAML changes are expensive, evaluate DRA extended-resource compatibility so applications can retain `resources.limits`.
6. Roll out advanced sharing, partitioning, device-taint, and health-status capabilities separately; do not enable everything by default.
7. Establish observability for ResourceClaim allocations, driver prepare/unprepare latency, Pod pending reasons, and device health.

Pay special attention to:

- Do not expose the same resource name on the same node through conflicting Device Plugin and DRA mechanisms, except through Kubernetes' supported DRA extended-resource migration path.
- DRA driver maturity is particularly important. A stable API does not make a particular vendor driver production-ready.
- Tie beta / alpha DRA features to the cluster-upgrade strategy; successful application of one YAML manifest is insufficient.
- Resource sharing does not guarantee reliable isolation. GPU memory, PCIe bandwidth, MPS, MIG, and vGPU isolation still depends on hardware and drivers.

## Common Misconceptions

### Dynamic Does Not Mean Runtime Hot-Plugging

DRA's "dynamic" primarily means that claims can select and allocate resources dynamically during scheduling. It does not mean a running Pod can add, remove, or replace GPUs at any time. Runtime changes still depend on Kubernetes, runtime, driver, and application capabilities.

### DRA Does Not Replace Vendor Drivers

DRA is a Kubernetes resource-allocation API, not a GPU driver, CUDA runtime, container toolkit, or RDMA user-space library. Nodes still need correctly installed hardware drivers and container-runtime integration.

### Device Plugins Are Not Unusable or Obsolete

Device Plugins are a mature production path. DRA is a more capable next-generation model, but Kubernetes versions, drivers, runtimes, monitoring, and operations must be ready before adoption.

### DRA YAML Is More Complex for a Reason

Device Plugin syntax is short:

```yaml
nvidia.com/gpu: 1
```

DRA is longer because it explicitly models information formerly hidden in node labels, plugin configuration, webhooks, scheduling extensions, and vendor-private logic. The complexity has moved from implicit behavior into standard API objects, rather than disappearing.

## Summary

Device Plugins and DRA are not simply old and new replacements. They represent two levels of abstraction:

- Device Plugins integrate devices with kubelet, focusing on what exists on a node and how containers can use it.
- DRA allocates resources through Kubernetes, focusing on workload requirements and how the scheduler selects, allocates, and tracks devices.

Device Plugins remain sufficient for simple GPU scenarios. For AI infrastructure, GPU virtualization, heterogeneous pools, sharing, and precise scheduling, DRA is the longer-term direction.
