### 1. Canary Deployment

#### Core Idea
**A gradual, controlled rollout**. Like miners sending a canary underground to detect toxic gas, this strategy first exposes a new application version to a small percentage of users, such as 1%, 5%, or 10%, to test it in real production conditions. If it works well, expand gradually until the old version is replaced. If problems appear, roll back immediately with limited impact.

#### Workflow
1.  **Initial state**: The stable old version, v1, receives 100% of user traffic.
2.  **Deploy the canary**: Deploy v2 without user traffic initially. Load balancer or service mesh rules, using tools such as Istio or Nginx, then direct a small group of users to v2: employees, users in certain regions, or randomly selected users.
3.  **Observe and monitor**: Closely monitor business metrics, such as order success rate and response time, and technical metrics, such as CPU usage and error rate.
4.  **Decision point**:
    *   **Success**: If the canary remains stable and metrics are healthy, gradually increase v2 traffic, for example 10% → 25% → 50% → 100%.
    *   **Failure**: Immediately route all traffic back to v1 and remove the faulty v2. Overall risk stays low because only a small user group was affected.
5.  **Complete rollout**: After v2 receives 100% of traffic and runs stably for a period, remove v1.

#### Advantages
*   **Very low risk**: Detect and fix problems before they affect many users.
*   **Live validation**: Tests use real users and traffic, yielding more reliable results.
*   **Smooth transition**: Little impact on users, often imperceptible.

#### Drawbacks
*   **Longer rollouts**: Gradually increasing traffic is slower than an all-at-once release.
*   **Deployment complexity**: Requires sophisticated traffic controls, such as a service mesh, and comprehensive monitoring and alerts.
*   **Two versions to maintain**: v1 and v2 must remain compatible throughout the rollout.

### 2. Blue-Green Deployment

#### Core Idea
**Switch environments instead of gradually shifting traffic**. Deploy two identical production environments, blue and green.
*   One, for example blue, serves all current production traffic.
*   The other, green, runs the new version.

After successful testing, change the load balancer configuration once to switch all traffic from blue to green. If green has problems, switch immediately back to blue.

#### Workflow
1.  **Initial state**: Blue, running v1, serves everyone. Green is idle or runs the same version.
2.  **Deploy the new version**: Install v2 in green and test it thoroughly with integration tests, API tests, and more. Live user traffic remains on blue.
3.  **Final checks**: Perform final health checks before switching traffic to green.
4.  **Switch traffic**: Change router, load balancer, or DNS configuration to move all production traffic from blue to green **at once**.
5.  **Observe and monitor**: Closely monitor green.
6.  **Decision point**:
    *   **Success**: Once green is stable, blue can be taken offline and become the "green" environment for the next release.
    *   **Failure**: Immediately switch all traffic back to blue, providing very fast rollback with almost no downtime.

#### Advantages
*   **Fast rollback**: Switching versions and rolling back requires only a routing change.
*   **Risk isolation**: Separate old and new environments avoid interference between versions.
*   **Clear, straightforward release and rollback procedures**.
*   **True zero-downtime deployment**.

#### Drawbacks
*   **High resource cost**: Two identical infrastructure environments double resource costs.
*   **Strict data compatibility requirements**: If both environments share a database during the switch, schemas and data must remain compatible in both directions or rollback can fail.
*   **All-or-nothing cutover**: Unlike canary releases, it cannot validate with a small user subset; everyone receives the new version together.

### Comparison

| Feature | Canary deployment | Blue-green deployment |
| :--- | :--- | :--- |
| **Core idea** | **Gradual** traffic shift | **One-time** environment switch |
| **Release speed** | Slower, incremental | Extremely fast, immediate |
| **Rollback speed** | Fairly fast, reduce traffic | **Extremely fast**, one switch |
| **Resource cost** | Lower, only extra partial capacity | **High**, two complete environments |
| **Risk control** | **Excellent**, limited impact | Good, but cutover affects all users |
| **Complexity** | High, fine-grained traffic controls | Medium, mainly infrastructure and routing |
| **Use cases** | User-facing applications needing business-logic validation | Infrastructure, middleware, or applications demanding very fast rollback |

### How to Choose

*   **Choose canary deployment** when new-version **stability and business impact** matter most, real-traffic gradual validation is desired, and a longer rollout is acceptable. Examples include e-commerce frontends and core transaction flows.
*   **Choose blue-green deployment** when **release and rollback speed** is paramount, resources are sufficient, or the application depends strongly on infrastructure. Examples include database upgrades, core middleware, and API gateways.

Production systems often combine both: build the new environment with blue-green deployment, then shift traffic gradually from blue to green using a canary approach instead of an all-at-once cutover, gaining advantages of both.
